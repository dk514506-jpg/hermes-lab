# Lakeview Loop Review Pattern

## Recurring critique signals

- Strong concept disclaimers are necessary but do not fully prevent implied affiliation when real businesses are named.
- A passport/progress metaphor becomes ambiguous if the UI shows numbered progress without defining what is recorded, who verifies it, or what the next action means.
- A static narrative is not a customer-flow prototype. Add a fixture-only state transition or narrow the claim.
- Choose one primary behavior hypothesis before presenting a network of different merchant economics.
- Treat staff SOP, measurement definitions, privacy, permission, and stop conditions as core product credibility—not appendix material.
- Use internal-only status when the source brief says publication/outreach is unauthorized.

## Accepted Lakeview revisions

- Reframed the shared system away from credits, points, balances, and prizes toward contextual visit records and configured next actions.
- Added an explicit primary hypothesis: test whether one verified interaction creates a useful next neighborhood action without requiring a fixed route or discounting every visit.
- Added a fixture-only `Record demo visit` / reset interaction labeled `DEMO DATA`.
- Added operator cards: Approve, Verify, Review.
- Added a narrow privacy statement acknowledging possible hosting/security logs.
- Added internal concept / review-before-external-sharing language.
- Added modal focus movement/restoration and review-only explanation.
- Created a pilot-readiness package and internal HTML pitch deck including Staff SOP, Measurement, Pilot Path, Privacy, and Governance slides.

## Operationalization checklist

1. Publication and permission status.
2. Evidence/naming reconciliation.
3. One primary behavior.
4. Interaction specification.
5. Staff SOP and fallback.
6. Privacy/consent package.
7. Private ledger controls.
8. Measurement baseline and stop conditions.
9. Reversible pilot charter.
10. Merchant-approved report and iteration decision.

## Verification pattern

Use a temporary `/tmp/hermes-verify-*.py` script and run it against the actual artifact. Check file existence, HTML tag counts, unique IDs, required content, forbidden scope strings, anti-drift vocabulary, inline JavaScript with `node --check`, and responsive CSS markers. Delete the temporary verifier. State that the result is ad-hoc targeted verification, not a full project suite.

# Phase 8 Evaluation Design Critique — Independent Judge (Claude Sonnet 4.5)

Evaluator: Claude Sonnet 4.5 (Anthropic API, independent of build)
Date: 2026-08-06
Artifacts evaluated: Phase 8 Evaluation directory (5 files) + whole-project review rubric
Method: Read all requested artifacts; assess discriminability, answerability, protocol soundness, calibration honesty, and gaps per the brief's five questions.

---

## Executive Summary

The Phase 8 evaluation design is **rigorous, self-critical, and operationally sound**. The 10 criteria discriminate quality effectively, the QA checklists are artifact-grounded and answerable, the scoring protocol is conservative (median aggregation, per-artifact floor, disagreement reconciliation), and the Calibration Log is an exemplary correction history. The evaluation design's own discipline (hypothesis-status, gap acknowledgment, verifier-vs-review boundaries) models the very criteria it measures.

**Strongest aspect:** The GAP discipline — 47 explicit **GAP** markers across the three checklists naming exactly which checks have no automated guard. This prevents the verifier coverage illusion and makes the evaluation honest about its limits.

**Sharpest finding:** The evaluation artifacts themselves carry meta-gaps — the checklists declare gaps in the *artifacts*, but no meta-verifier checks whether the *checklists* themselves are complete against the rubric. The evaluation layer is unguarded.

**Verdict:** PASS with revision — the evaluation design is deployable as-is for this campaign; the five recommendations below would strengthen it for reuse or adaptation to other projects.

## Question 1: Do the 10 criteria discriminate quality?

### Answer: YES — all 10 criteria would yield 0 for weak artifacts and 2 for strong ones.

**Evidence from the rubric (Evaluation_Rubric.md):**

Each criterion defines a **3-point ladder** (0/1/2) with explicit artifact-level conditions:

- **C1 (AtomicOp decomposition):** 0 = no atomic_ops.json or ops non-executable; 1 = ops exist but some lack inputs/outputs/guardrails, or T2R incomplete, or decomposition edges inconsistent; 2 = all ops fully specified, T2R-traced, direction-consistent, verifier-guarded. **Discriminates:** a package with malformed JSON would score 0; a package with ops but missing guardrails would score 1; only a complete, verified package scores 2.

- **C3 (Empowerment boundary):** 0 = no empowerment boundary anywhere; 1 = boundary in prose only (nodes lack boundary_gate, no preserved-user-decision output, no debrief section, or gate not runtime-enforced); 2 = structural (gate required on all nodes, preservation outputs + debrief recording + log boundary_gate_outcome event), verifier-guarded. **Discriminates:** the prose-vs-structural split is the exact question a quality check should ask.

- **C6 (Evidence citation):** 0 = insights uncited or flags absent; 1 = flags present but drift (opinion cited as VERIFIED, preprint unflagged, register-only source cited as evidence) or flags live only in prose/comments; 2 = structural flags + caveat discipline + integrity register + verifier-guarded. **Discriminates:** a weak artifact with claims in prose but no data-level flags would score 1; only disciplined flagging scores 2.

- **C7 (User correction of insights):** 0 = no user-verdict mechanism (insights treated as facts); 1 = correction possible in prose but not structural (no verdict state, no quarantine op, corrections not logged); 2 = verdict recorded as state + quarantine enforced + corrections appended to logs + debrief carries preserved decisions. **Discriminates:** this is the hypothesis-vs-doctrine divide Valens discipline requires.

All 10 criteria follow this pattern: 0 = absent/contradicted, 1 = present-but-not-structural/partial/unguarded, 2 = structural + consistent + verifier-guarded. The ladder is **not a Likert scale** (agree/disagree) but a **realization ladder** (missing → declared → enforced). A weak artifact that talks about empowerment but doesn't encode it would score 1; only operational encoding scores 2.

**One refinement point (C4/C5):** C4 and C5 both cap at 1 "until a runtime record exists" — the rubric is honest that schema + ops + policy are not the same as logged execution. This is correct discipline, but it means **every artifact scores ≤1 on C5 by construction** (no runtime logs exist in the campaign tree; logs/ ships empty per verify_phase7 check). The criterion discriminates schema-present from schema-absent, but cannot discriminate good runtime logging from bad because no runtime exists. This is acknowledged in the rubric (C5 ladder: "Cap at 1 until a runtime record exists"), so it's not a flaw — but it does mean C5 is a **future-readiness check**, not a current-artifact check. Recommendation: either accept C5 as a 0-vs-1 discriminator for this phase, or defer C5 to a Phase 9 runtime evaluation and score only C1-C4, C6-C10 here.

## Question 3: Is the scoring/aggregation protocol sound?

### Answer: YES — the protocol is conservative and prevents gaming.

**Protocol summary (Evaluation_Rubric.md §1.3):**

1. **Per-criterion score = median** of all scores (Council + judges), rounded to nearest integer. Median is robust to outlier disagreement — one judge scoring 0 when the Council scores 2 won't skew the result as mean would.

2. **Disagreement ≥1 point between Council and any judge forces a written reconciliation note** into Calibration_Log.md (finding → fix → guard). This prevents silent divergence and creates an audit trail.

3. **Overall score = mean across 10 criteria.** Bands: PASS ≥1.8, WARN 1.2–1.79, FAIL <1.2. A project scoring 2 on nine criteria but 0 on one would score 1.8 overall (PASS floor) — this is lenient, but the next rule tightens it.

4. **Per-artifact floor: a criterion scored 0 on any artifact blocks that artifact's PASS** (Evaluation_Rubric.md line 52-53). Example: if C6 (evidence citation) scores 0 for the TDF package (no flags), the TDF package is blocked even if the overall score is ≥1.8. This prevents a strong average from hiding a broken part.

**Why this is sound:**

- **Median scoring resists inflation.** A 3-judge panel scoring [0, 1, 2] yields median 1, not mean 1.0. A council that over-scored would need ≥2 judges to also over-score to shift the median.

- **Disagreement reconciliation is mandatory.** If Council scores C3 as 2 ("empowerment boundary is structural") and Judge scores it 0 ("no boundary gate exists"), the ≥1-point gap triggers a reconciliation. The finding must be recorded in Calibration_Log with (a) which artifact, (b) what was wrong, (c) how it was fixed, (d) which verifier now guards it. This forces honesty.

- **The per-artifact floor is the right gate.** Without it, a campaign could ship eight strong packages and two broken ones and claim PASS. The floor ensures every governed artifact meets the threshold. (Note: the rubric says "a criterion scored 0 on any artifact it governs blocks that artifact's PASS" — this is per-artifact, not per-criterion globally, which is correct. A 0 on C6 for TDF blocks TDF, not the whole campaign.)

**One ambiguity (clarification needed):** The rubric says "per-criterion score = median ... per artifact" (line 43-44) but also "overall score = mean across the 10 criteria" (line 47). Is the overall score per-artifact (mean of 10 criteria for that artifact) or global (mean of 10 criteria across all artifacts)? Reading §1.3 in full: the per-artifact floor (line 52) implies per-artifact scoring, so I interpret it as: each artifact gets 10 criterion scores → median per criterion → mean across criteria = artifact overall score → PASS/WARN/FAIL per artifact. The campaign PASSes if all governed artifacts PASS. **Recommendation:** make this explicit in §1.3 ("each artifact is scored independently; the campaign PASSes when all artifacts PASS").

**Bands calibration:** PASS ≥1.8 means an artifact can score 1 (partial) on two criteria and still pass if it scores 2 on the other eight (10×2 − 2×1 = 18 → 18/10 = 1.8). Is this too lenient? No — because the ladder definition makes 1 = "present but not structural/not guarded", which is a real intermediate state (the work exists but needs hardening). A WARN (1.2–1.79) would mean 4–8 criteria at partial, which is "usable but carries open items" — reasonable. FAIL (<1.2) means ≥9 criteria partial or 1 criterion absent — correctly harsh.

**Verdict on Q3:** The protocol is sound. Median + disagreement-reconciliation + per-artifact floor is a **conservative, audit-trailed, non-gameable** design.

## Question 4: Is the Calibration_Log complete and honest?

### Answer: YES — it is the campaign's exemplary self-correction record.

**What makes a calibration log "complete and honest"?**

1. **Every review-round correction is recorded** (not just the fixes that survived, but the errors that were caught).
2. **Each entry names the artifact** that was wrong (not abstract "we improved the evidence discipline").
3. **Each entry states the verifier guard** that now holds the fix (or "no automated guard — review-round enforced" when none exists).
4. **Open items are preserved, not closed prematurely.**

**Evidence from Calibration_Log.md:**

- **16 corrections recorded** (rows 1–16 in §1), spanning Phases 3–7. Each row: phase/round, finding (artifact-referenced), fix applied, verifier guard. Example row 5 (Phase 4 critique): "Edge direction contradiction: index declared flagship `decomposes_to COMB→TDF` ... but no package map carried it; TDF's own map declared the REVERSE `supports TDF→COMB` ... verifiers were direction-blind ... Fix: Single typed edge retained ... Index note: 'RECONCILED 2026-08-06' ... Verifier guard: verify_critique_revisions.py checks 4-5 ... verify_phase4.py (source/target normalization, recovers_with directions + kind)." This is **artifact-specific, fix-specific, and guard-specific** — the gold standard for a correction record.

- **6 standing calibration items** (Q6–Q11 in §2) that remain OPEN. Q10 ("Campaign self-application: is Dallas deskilled by councils that read for him?") is particularly honest — the campaign is naming its own over-assistance risk and tracking per-phase unassisted user work. Q11 (HEB runtime enforcement) is marked PARTIALLY RESOLVED with the open tail explicit ("execution-layer wrapper ... is the open tail"). These are not swept under "future work" — they're named, witnessed, and carry forward into Phase 8 evaluation as checklist questions.

- **Verifier register** (§3) lists the eight verifiers, their scope, and check counts. This is the "guards referenced above" index — a rater reviewing row 5 can see that verify_critique_revisions.py is a real tool, not a promise.

- **Honest failure admissions.** Row 1 (Phase 3 critique): "README claimed 'all VERIFIED' — false: the bibliography itself carries UNVERIFIED [28],[75], RECONSTRUCTED [22],[27] ... Flag semantics drift at the summary layer." The log doesn't soften this ("we clarified our terminology") — it says "false" and names the exact entries. Row 10 (Phase 7 DeepSeek R2): "Index/package edge divergence: 75 cross-skill edges in the eight package edge_maps absent from the index's 10 edges ... Fix: Index explicitly declared a **curated canonical subset** ... Full edge-set diff remains a build-time manual audit; documented as such." The log admits the divergence, states the resolution (subset rule), and is honest that full parity is manual. No pretense.

**What would make it incomplete?** If corrections were recorded without artifact references ("we improved evidence discipline" — where?), or fixes were claimed without verifier guards ("we now check flags" — which check?), or open items were quietly closed, or past errors were memory-holed. None of these faults are present.

**One question (depth vs breadth):** The log records 16 corrections across 5 phases. How many errors were there total, and are these 16 the complete set or a sample? The log says "every review-round correction caught in this campaign is recorded below" (line 6-7), so this should be complete. But verify: the Phase 3 critique (critique_0) is cited in rows 1–4; did that critique raise other findings not in the log? I cannot verify completeness without reading critique_0 itself (not provided in the brief), but the log's claim is explicit and falsifiable. If a future audit finds uncorrected critique findings, the log would be proven incomplete. Absent that, I take the log at its word.

**Verifier-guard honesty:** 6 of the 16 rows say "no automated guard" or "revision-round enforced" (rows 1, 3, 8, 16 governance entries). The log doesn't pretend everything is machine-checked — it names the review-only checks. This is honest about the limits of automation.

**Verdict on Q4:** The Calibration_Log is **complete, honest, artifact-grounded, and self-critical**. It is the strongest single artifact in the Phase 8 package.

## Question 5: What is MISSING from the evaluation design?

### Strong foundations observed first:

1. **The rubric operationalizes the 10 plan criteria** against named artifacts with 0/1/2 ladders (Evaluation_Rubric.md).
2. **Three sibling checklists** apply the rubric to the skill-package layer (Skill_Package_QA_Checklist.md, 8 packages × criteria 1–5 + state coherence), the lattice layer (Motivational_Lattice_QA_Checklist.md, criteria 6, 7, 10), and the dojo layer (Practice_Dojo_QA_Checklist.md, criteria 8, 9 + executor), with 47 explicit **GAP** markers where no verifier guards the check.
3. **Calibration_Log.md** records 16 corrections + 6 standing open items with artifact-referenced findings, fixes, and verifier guards.
4. **Outside-judge round** is designed (Evaluation_Rubric.md §1.2) with cross-provider critique (Claude + DeepSeek or second API) and sublative integration (preserve kernel, negate weak, raise).
5. **Verifier chain** (verify_all.py) runs at every gate; all must exit 0.

### Five categories of missing elements:

#### 5.1 Meta-evaluation gap: the evaluation artifacts themselves are unguarded

**What's missing:** A verifier for the Phase 8 evaluation design itself.

**The gap:** The three checklists declare 47 **GAP** markers in the skill/lattice/dojo artifacts, and verify_phase3–7.py enforce structure. But **nothing checks whether the checklists are complete** against the rubric. Questions:

- Does Skill_Package_QA_Checklist.md cover all 10 criteria for all 8 packages, or did a package × criterion cell get skipped?
- Do the three checklists' criteria coverage sum to the 10 rubric criteria (skill package covers 1–5, lattice covers 6/7/10, dojo covers 8/9 — is that exhaustive)?
- Does every GAP marker in the checklists name a proposed verifier guard (or explain why none is feasible)?

**Why this matters:** If a criterion is missing from the checklists, the evaluation would silently skip it. The rubric is the contract; the checklists are the instrument; no check ensures the instrument covers the contract.

**Recommendation:** Write `verify_phase8.py` with checks:
1. Coverage: parse the three checklists and verify that all 10 criteria (C1–C10) are represented ≥1 time each.
2. Artifact inventory: verify that all 8 skill packages, the lattice index, and all 5 dojos have ≥1 checklist row each.
3. GAP discipline: every **GAP** marker must appear in a row with an "Enforcement" or "Verifier guard" column that either names a verifier or says "GAP — no guard" or "PARTIAL — presence only".
4. Reconciliation notes referenced: every Rn reference (R1–R4 in Skill_Package_QA_Checklist) must have a corresponding section in the checklist or handoff_notes.md.

This would close the meta-evaluation loop.

#### 5.2 Sampling and coverage strategy for review-enforced checks

**What's missing:** Guidance on **how to sample** the 47 GAPs when no verifier checks them.

**The gap:** Many checks are marked **GAP** with "review-enforced" or "no verifier checks the *substance*". Examples:
- Skill_Package_QA_Checklist.md: "Evidence citations (#6, #10)" is GAP for all 8 packages — "no verifier scans for citations or VERIFIED/RECONSTRUCTED flags (review-enforced; see Calibration_Log catches)".
- Motivational_Lattice_QA_Checklist.md, L1: "The *wording* rule (Gate A #5) is **GAP** — no verifier reads hypothesis phrasing".
- Practice_Dojo_QA_Checklist.md, all five dojos: "Rubric-as-lens" is PARTIAL — "lens type + use-rules presence ENFORCED; the `scoring.anchoring` string ... is not machine-checked".

A rigorous evaluator would ask: **How many of the 47 GAPs should I manually check, and which ones?** The evaluation design doesn't say. Without a sampling protocol, a rater might spot-check 3 GAPs (non-representative) or attempt all 47 (infeasible).

**Recommendation:** Add an **Evaluation Sampling Protocol** section to Evaluation_Rubric.md:
- **Tier 1 (mandatory manual checks):** All GAPs that guard safety invariants (sycophancy guard content, no-surveillance prose, spirit-gate/de-escalation prose, hypothesis-status wording, user-rejection-absolute). Sample: 10–12 checks.
- **Tier 2 (random sample):** Evidence-citation presence (≥1 VERIFIED source per package), state-schema↔SKILL.md name parity, completion-conditions terminal-op presence. Sample: 20% of packages/dojos (2 packages, 1 dojo).
- **Tier 3 (conditional):** Trigger T1–T6 policy↔index parity, lattice-skill-edges↔MLG-edge-map parity — check these if any judge or Council member raises a lattice-coherence concern; otherwise defer (one-time checks already done in Calibration_Log row 10/14 reconciliation).

This would make "review-enforced" actionable instead of aspirational.

#### 5.3 Inter-rater reliability and disagreement thresholds

**What's missing:** Expected agreement rate and what to do when judges split 3 ways.

**The gap:** The protocol says "disagreement ≥1 point between Council and a judge forces a written reconciliation note" (Evaluation_Rubric.md line 46), but:
- What if Council scores 2, Judge A scores 1, Judge B scores 0? The median is 1, but there's ≥1-point disagreement Council↔B (2 vs 0) **and** A↔B (1 vs 0). Does this trigger two reconciliation notes, or one?
- What disagreement rate is acceptable? If 5 of 10 criteria show ≥1-point splits, is the evaluation instrument broken, or is that normal for an outside-judge round?

**Why this matters:** The Calibration_Log (row 8, Jose 2025 opinion flag; row 7, CALM-IT preprint) shows verifier guards were added **because a review round caught the drift**. If every criterion triggers disagreement, the reconciliation load could stall the round. Conversely, if zero disagreement occurs, the judges might be redundant (Council self-review would suffice).

**Recommendation:** Add a **Disagreement Budget** section to Evaluation_Rubric.md §1.3:
- **Expected range:** 2–4 criteria (of 10) showing ≥1-point Council↔judge disagreement is normal for a rigorous outside-judge round; 0–1 suggests judges aren't independent; ≥6 suggests the rubric is ambiguous or the artifacts are inconsistent.
- **Reconciliation protocol:** Each ≥1-point disagreement gets one reconciliation note (Council + all dissenting judges' findings combined), not one note per judge pair.
- **Threshold for rubric revision:** If ≥6 criteria split, pause and revise the rubric (clarify the ladder) before continuing the round.

This would set expectations and prevent reconciliation overload.

#### 5.4 Self-application and the Q10 loop

**What's missing:** Concrete measurement of the campaign's own skill-load impact on Dallas.

**The gap:** Q10 (Calibration_Log.md line 46) asks "Campaign self-application: is Dallas deskilled by the councils that read for him?" The log says "per-phase record of unassisted user work; Phase 8 review of these artifacts is itself a Q10-relevant unassisted act" and "C5: the rubric's own evaluation must not over-assist; record what Dallas does unassisted." But **no such record exists** in the artifacts I read. handoff_notes.md (referenced in the review rubric line 31) would be the natural home, but I don't see a "Dallas unassisted work log" or "per-phase user decision inventory" there.

**Why this matters:** Q10 is the campaign's integrity test. If Pip (the agent) generated all 8 skill packages, wrote the checklists, ran the critiques, and Dallas only approved/rejected, the campaign would have deskilled Dallas (skill_load falling trend, atrophy risk rising). But if Dallas authored the theory layer, corrected council outputs, adjudicated conflicts, and made scope decisions, the campaign would be scaffolding → fade (skill_load maintained or rising, capability-building). The rubric acknowledges this (C5: "campaign's own self-application record") but provides no data.

**Recommendation:** Add a **Self-Application Log** to handoff_notes.md or council_notes/:
- Per phase: What did Dallas do unassisted (wrote Foundation_Matrix from scratch, corrected edge-direction contradiction in Phase 4, decided Q6 TDF versioning stays open)?
- What did Pip/councils do with Dallas approval only (council-generated skill packages, judge-round critiques)?
- What did Dallas delegate to subagents and then QA (evidence digest)?
- Assistance fraction per phase (0 = Dallas solo, 1 = councils solo, 0.3–0.7 = collaborative).

Then evaluate: is Dallas's capability rising (he can now author a skill package solo), flat (he can QA one but not author), or falling (he approves council packages without understanding them)? This would operationalize Q10 instead of leaving it rhetorical.

#### 5.5 Deployment and iteration criteria

**What's missing:** What happens after this evaluation round — when is the harness "done"?

**The gap:** The rubric defines PASS/WARN/FAIL bands (Evaluation_Rubric.md line 47-51) and the per-artifact floor (line 52-53), but it doesn't say:
- **What does PASS mean for deployment?** Is a PASSing artifact uploaded to OneDrive/SharePoint as-is (Q8 standing item references this), shared publicly, integrated into a Hermes installation, all three, or something else?
- **What triggers a Phase 9?** The plan says this is Phase 8 of 8 (Evaluation_Rubric.md line 4). If the evaluation yields WARN (1.2–1.79), does the campaign iterate to Phase 9 (remediation round), or does it close with WARN status and the open items tracked?
- **What is the acceptance test for "usable in a home lab"?** The whole-project rubric (review_rubric.md line 107-108) says the purpose is "a governed learning-and-agency-support architecture for a home-lab Hermes harness". Who decides if it's usable — Dallas (the user), an independent installer, a third party?

**Why this matters:** Without deployment criteria, the evaluation is a grade without a decision. The campaign could PASS the evaluation but never ship (perfectionism trap), or WARN but ship anyway (deployment-pressure override). The rubric should state the deployment rule.

**Recommendation:** Add a **Deployment and Iteration Protocol** section to Evaluation_Rubric.md:
- **PASS (≥1.8, no 0-scoring artifacts):** Harness is uploadable to the OneDrive/SharePoint path (Q8) and installable by a fresh Hermes instance per the README. Open items (Q6, Q7, Q10, Q11) are tracked in handoff_notes.md as standing calibrations, not blockers. The campaign closes at Phase 8; future work is deferred or separately scoped.
- **WARN (1.2–1.79):** Harness is usable but not claimable as "complete". Remediation plan required: fix the 0-scoring artifacts (if any) and raise ≥2 partial criteria to full (target: overall ≥1.8). Phase 9 = remediation round, re-evaluated per this rubric.
- **FAIL (<1.2, or any 0-scoring artifact persists after one revision):** Campaign pauses; root-cause the evaluation failures (rubric ambiguity? artifact incompleteness? scope creep?); revise Phase 8 plan or abort the campaign and document lessons learned.
- **Acceptance test (usability):** Dallas installs the harness in a fresh Hermes profile, runs one dojo session (any dojo), and confirms: (a) the session runs per the artifacts, (b) the logs conform to log_schema.md, (c) the governance rules (boundary gate, fade policy) are observable in the session flow. If all three hold, the harness is usable. If not, the evaluation missed a runtime gap — escalate to WARN and document the gap.

This would close the evaluation → deployment loop.

A rater can answer this with a 2-file diff.

### 4. **Verifier register (Calibration_Log.md §3)**
Lists the eight verifiers, their scope, and check counts (verify_phase3.py: structural, all 8; verify_phase5.py: 21 checks + guards; verify_phase6.py: all 5 dojos, generic + owned). This is the "guards referenced above" index — a rater reviewing a Calibration_Log row can verify that the claimed guard exists. Prevents guard-promise drift.

### 5. **Conservative scoring protocol**
Median aggregation (robust to outliers) + disagreement reconciliation (≥1-point gap → written note) + per-artifact floor (a 0 on any criterion blocks that artifact's PASS) is **non-gameable**. A council that over-scored would need ≥2 judges to also over-score to shift the median, and any disagreement would trigger a reconciliation note naming the finding/fix/guard.

## Weaknesses (What is missing or weak)

### 1. **Meta-evaluation gap: the checklists are unguarded**
No verifier checks whether the three checklists cover all 10 criteria for all governed artifacts. If Skill_Package_QA_Checklist.md skipped a package × criterion cell, the evaluation would silently miss it. **Fix:** Write verify_phase8.py (coverage, GAP discipline, reconciliation-note references) per §5.1.

### 2. **No sampling protocol for the 47 GAPs**
The checklists mark 47 checks as GAP or PARTIAL (review-enforced, not machine-checked), but the rubric doesn't say how many to manually check or which ones. A rater could spot-check 3 (non-representative) or attempt all 47 (infeasible). **Fix:** Add an Evaluation Sampling Protocol (Tier 1 mandatory safety checks, Tier 2 random sample, Tier 3 conditional) per §5.2.

### 3. **Disagreement threshold undefined**
The protocol mandates reconciliation for ≥1-point disagreements but doesn't say what disagreement rate is acceptable (0–1 criteria? 5 of 10?) or what to do when judges split 3 ways (Council 2, Judge A 1, Judge B 0 → two notes or one?). **Fix:** Add a Disagreement Budget (expected 2–4 criteria, threshold ≥6 = rubric revision) per §5.3.

### 4. **Q10 (self-application) is rhetorical, not measured**
The campaign acknowledges the over-assistance risk (Calibration_Log Q10, rubric C5) but provides no data on Dallas's unassisted work per phase. **Fix:** Add a Self-Application Log (per-phase unassisted work, assistance fraction, capability trend) per §5.4.

### 5. **Deployment criteria absent**
The rubric defines PASS/WARN/FAIL but doesn't say what happens after — is a PASSing harness uploaded, installed, tested, all three? What triggers a Phase 9 remediation round? **Fix:** Add a Deployment and Iteration Protocol (PASS = uploadable, WARN = remediation plan, FAIL = pause, acceptance test = Dallas installs and runs one session) per §5.5.

## Five Concrete Recommendations (Priority-Ordered)

### R1. Write `verify_phase8.py` to guard the evaluation artifacts themselves (§5.1)
**Why:** The checklists declare 47 GAPs in the governed artifacts, but nothing checks whether the checklists are complete against the rubric. This is the meta-evaluation gap.

**What:** A verifier with four checks:
1. **Coverage:** Parse the three checklists (Skill_Package_QA, Motivational_Lattice_QA, Practice_Dojo_QA) and verify that all 10 criteria (C1–C10) are represented ≥1 time each across the three files.
2. **Artifact inventory:** Verify that all 8 skill packages (HEB, COMB, TDF, SDT, MI, PPS, MLG, ConvoDojo), the lattice index, and all 5 dojos (Conversation, Coaching, Ambivalence, Conflict, Workplace) have ≥1 checklist row each.
3. **GAP discipline:** Every **GAP** or **PARTIAL** marker must appear in a row with an "Enforcement" or "Verifier guard" column that either names a verifier (verify_phaseN.py check M) or explicitly says "GAP — no guard" or "PARTIAL — presence only".
4. **Reconciliation notes:** Every Rn reference (R1–R4 in Skill_Package_QA_Checklist) must have a corresponding section in the checklist's "Reconciliation Notes" or in handoff_notes.md.

**Priority:** HIGH — this closes the self-evaluation loop and prevents silent checklist incompleteness.

### R2. Add an Evaluation Sampling Protocol to Evaluation_Rubric.md (§5.2)
**Why:** 47 checks are marked GAP/PARTIAL (review-enforced, not machine-checked). A rigorous evaluator needs guidance on how many to manually check and which ones.

**What:** A new section in Evaluation_Rubric.md §1.5 "Sampling Protocol for Review-Enforced Checks":
- **Tier 1 (mandatory, ~10–12 checks):** All GAPs that guard safety invariants:
  - Sycophancy guard content (all 5 dojos, Practice_Dojo_QA 2.1–2.5 rows)
  - No-surveillance prose (lattice layer L6, dojo layer 2.1–2.5)
  - Spirit-gate / de-escalation-first prose (Ambivalence 2.3, Conflict 2.4)
  - Hypothesis-status wording (lattice L1, skill packages COMB/TDF/MI)
  - User-rejection-absolute invariant (lattice L2.Q3)
- **Tier 2 (random 20% sample, ~8 checks):** Evidence-citation presence (≥1 VERIFIED source per skill package → sample 2 of 8), state-schema↔SKILL.md name parity (sample 2 of 8), completion-conditions terminal-op presence (sample 2 of 8), rubric anchoring (sample 1 of 5 dojos).
- **Tier 3 (conditional, ~4 checks):** Trigger T1–T6 policy↔index parity, lattice-skill-edges↔MLG-edge-map parity — check only if a judge or Council member raises a lattice-coherence concern; otherwise defer (one-time checks already done in Calibration_Log row 10/14 reconciliation).

**Priority:** HIGH — this makes "review-enforced" actionable instead of aspirational.

### R3. Add a Deployment and Iteration Protocol to Evaluation_Rubric.md (§5.5)
**Why:** The rubric defines PASS/WARN/FAIL but doesn't state what happens after the evaluation — when is the harness "done"? Without deployment criteria, the evaluation is a grade without a decision.

**What:** A new section in Evaluation_Rubric.md §1.6 "Deployment and Iteration Protocol":
- **PASS (≥1.8, no 0-scoring artifacts):** Harness is uploadable to OneDrive/SharePoint (Q8) and installable per README. Open items (Q6, Q7, Q10, Q11) tracked in handoff_notes.md as standing calibrations, not blockers. Campaign closes at Phase 8.
- **WARN (1.2–1.79):** Usable but not complete. Remediation plan: fix any 0-scoring artifacts + raise ≥2 partial criteria to full (target ≥1.8). Phase 9 = remediation round, re-evaluated per this rubric.
- **FAIL (<1.2, or 0-scoring artifact persists after one revision):** Pause; root-cause the failures (rubric ambiguity? artifact incompleteness?); revise Phase 8 plan or document lessons learned and close.
- **Acceptance test (usability):** Dallas installs the harness in a fresh Hermes profile, runs one dojo session, confirms: (a) session runs per artifacts, (b) logs conform to log_schema.md, (c) governance rules observable. If all three hold → usable. If not → WARN + document the runtime gap.

**Priority:** HIGH — this closes the evaluation → deployment loop and defines "done".

### R4. Add a Self-Application Log to handoff_notes.md (§5.4)
**Why:** Q10 (campaign self-application: is Dallas deskilled?) is acknowledged in Calibration_Log and rubric C5 but unmeasured. The campaign's integrity test requires data.

**What:** A new section in handoff_notes.md "Self-Application Record (Q10)":
- **Per phase:** What Dallas did unassisted (Phase 1: authored Foundation_Matrix from scratch; Phase 4: corrected edge-direction contradiction, decided Q6 stays open; Phase 7: adjudicated judge-round conflicts), what Pip/councils did with approval only (Phase 3: council-generated 8 skill packages, Dallas QA'd and corrected 3), what was delegated to subagents and then QA'd (Phase 2: evidence digest).
- **Assistance fraction:** Per phase, estimate 0 = Dallas solo, 1 = councils solo, 0.3–0.7 = collaborative.
- **Capability trend:** Rising (Dallas can now author a skill package solo after scaffolding in Phase 3), flat (can QA but not author), falling (approves without understanding).
- **Phase 8 unassisted:** Dallas reads the five evaluation artifacts, runs the judge brief, integrates judge findings — this is itself a Q10-relevant act (unassisted evaluation work).

**Priority:** MEDIUM — operationalizes Q10; not a blocker for evaluation but required for campaign integrity claim.

### R5. Add a Disagreement Budget to Evaluation_Rubric.md §1.3 (§5.3)
**Why:** The protocol mandates reconciliation for ≥1-point disagreements but doesn't set expectations (how many splits are normal?) or resolve 3-way splits (Council 2, Judge A 1, Judge B 0 → two notes?).

**What:** Extend Evaluation_Rubric.md §1.3 with a "Disagreement Budget" subsection:
- **Expected range:** 2–4 criteria (of 10) showing ≥1-point Council↔judge disagreement is normal for a rigorous outside-judge round; 0–1 suggests judges aren't independent; ≥6 suggests rubric ambiguity or artifact inconsistency.
- **Reconciliation protocol:** Each ≥1-point disagreement gets one reconciliation note (Council + all dissenting judges' findings combined), not one note per judge pair. Example: Council scores C3 as 2, Judge A scores 1, Judge B scores 0 → one note titled "C3 Empowerment Boundary: Council(2) vs A(1) vs B(0)" with all findings + fix + guard.
- **Threshold for rubric revision:** If ≥6 criteria split, pause the outside-judge round and revise the rubric (clarify the 0/1/2 ladder for the ambiguous criteria) before continuing.

**Priority:** MEDIUM — prevents reconciliation overload and sets quality expectations for the judge round.
